# Airline Reservation System — Backend

Backend for a single-airline reservation system: flight schedule management, airport/aircraft
onboarding, flight search, seat inventory, ticket booking, and cancellation — secured with
role-based JWT auth (`ADMIN` / `CLIENT`) issued by a login endpoint. Spring Boot 4.1.1 / Java 22 /
MySQL.

## Repository layout (and deviations from the suggested layout)

```
├── README.md
├── hld/architecture.md     # high-level design + Mermaid diagrams
├── lld/design.md           # low-level design: modules, APIs, validation, transactions
├── db/schema.sql           # generated reference dump of the final schema (see note below)
├── docker-compose.yml      # local MySQL for `./mvnw spring-boot:run`
├── pom.xml
└── src/
    ├── main/java/com/airline/booking/   # application code
    ├── main/resources/db/migration/     # Flyway migrations — see note below
    └── test/java/com/airline/booking/   # tests
```

The assignment's suggested layout lists a top-level `/src`, `/tests`, and `/db/schema.sql` +
`/db/migrations/`. Two of these conflict with Maven's hard requirements (`src/main/java` and
`src/test/java` are fixed, not stylistic choices), so:

- `/src` already sits at the repo root via Maven convention — satisfies the spec as written.
- **Tests live at `src/test/java`**, not a top-level `/tests` folder.
- **Flyway migrations live at `src/main/resources/db/migration`** (Spring Initializr's own
  scaffold, and Flyway's classpath-default location) rather than a top-level `/db/migrations`.
  This was a deliberate choice over pointing Flyway at `filesystem:db/migrations`: a filesystem
  location resolves relative to the JVM's working directory, which is fragile the moment the app
  is packaged as a jar or containerized (you'd have to make sure the migrations directory ships
  alongside it and the working directory is right). The classpath default bakes migrations into
  the jar and works regardless of how or from where it's run. `db/schema.sql` at the repo root is
  generated by concatenating the real migration files (see its header) so the spec's expected path
  still exists, as a reference.
- `hld/architecture.md` (Markdown + Mermaid) substitutes for `architecture.pdf` — no PDF tooling
  was available, and Mermaid renders natively on GitHub/most doc viewers and is diff-reviewable.
  Diagrams are embedded inline in that file rather than a separate `hld/diagrams/` folder, since
  Mermaid source *is* the diagram — there's no separate rendered-image artifact to store.
- `docker-compose.yml` is present at the repo root exactly as the suggested layout names it; it's
  also one of the filenames Spring Boot's docker-compose support auto-detects, so it doubles as
  both the deliverable and the file `./mvnw spring-boot:run` actually uses — no duplicate/second
  compose file to keep in sync. It also declares the app itself as a second service, gated behind
  a `standalone` Compose profile (see **Running fully containerized** below) — the profile guard
  stops `./mvnw spring-boot:run` from trying to build and launch a containerized copy of itself,
  since Spring Boot's docker-compose support otherwise auto-starts every un-profiled service in
  this file.

## Setup / Build / Run

**Requirements**: JDK 22, a Docker-compatible container runtime (Docker Desktop, or Colima/Podman —
Docker Desktop requires macOS Sonoma+; on older macOS use `brew install colima docker` then
`colima start`).

```bash
# Build + run tests (spins up MySQL via Testcontainers automatically)
./mvnw test

# Run the app (uses docker-compose.yml to start a local MySQL automatically via
# spring-boot-docker-compose; Flyway migrates the schema and seeds reference data on startup)
./mvnw spring-boot:run
```

No manual database setup is required for either path — Testcontainers (tests) and
spring-boot-docker-compose (`spring-boot:run`) both provision MySQL and run migrations
automatically. To connect manually instead, `docker-compose.yml` defines `airline`/`airline`/`airline`
on `localhost:3306`.

### Running without Docker/Testcontainers

If no Docker-compatible runtime is available, install MySQL natively instead (e.g.
`brew install mysql`), create the `airline` database/user to match `docker-compose.yml`'s credentials,
then run with `spring.docker.compose.enabled=false` and explicit datasource properties pointing at
`localhost:3306` (see `application-local.properties` if present, or pass them as
`-D`/environment overrides).

### Running fully containerized (app + MySQL)

```bash
# Builds the app image, then starts MySQL and the app together on one Docker network
docker compose --profile standalone up -d --build

# Tear down
docker compose --profile standalone down
```

The app reaches MySQL over the Compose network by service name (`jdbc:mysql://mysql:3306/airline`)
— no `host.docker.internal` needed. `--profile standalone` is required because the `app` service is
deliberately excluded from the default profile (see **Repository layout** above).

To build and run the image manually instead, without Compose managing the app:

```bash
docker build -t booking:latest .
docker run -d --name booking-app -p 8080:8080 \
  -e SPRING_DOCKER_COMPOSE_ENABLED=false \
  -e SPRING_DATASOURCE_URL=jdbc:mysql://host.docker.internal:3306/airline \
  -e SPRING_DATASOURCE_USERNAME=airline \
  -e SPRING_DATASOURCE_PASSWORD=airline \
  booking:latest
```

(`host.docker.internal` is how a standalone container reaches a port published by another
container, when the two aren't on a shared Compose network — use this form if MySQL is running as
its own plain container via `docker compose up mysql` rather than the full `standalone` profile.)

## Authentication

JWT bearer tokens, two seeded in-memory users (`SecurityConfig`) exchanged for a token at a single
login endpoint — no credentials are sent on any other request:

| Username | Password | Role |
| --- | --- | --- |
| `admin` | `admin123` | `ADMIN` |
| `client` | `client123` | `CLIENT` |

```
POST /api/v1/auth/login          -- public, no auth required
{ "username": "admin", "password": "admin123" }

200 OK
{ "token": "<JWT>", "tokenType": "Bearer", "role": "ADMIN", "expiresInSeconds": 3600 }
```

Every other protected request carries `Authorization: Bearer <token>`. The token is a signed
(HS256) JWT whose `role` claim is the sole source of authorization (`JwtAuthenticationFilter`
reads it; nothing is looked up from a session or database on each request — auth is fully
stateless). Tokens expire after `app.jwt.expiration-minutes` (60 by default) — log in again to get
a fresh one.

| Endpoint group | Required role | No/invalid token | Wrong role |
| --- | --- | --- | --- |
| `POST /api/v1/auth/login` | none — public | — | — |
| `GET /api/v1/flights/**` (search, seat map) | none — public | — | — |
| `/api/v1/admin/**` (schedules, airports, aircraft) | `ADMIN` | 401 | 403 |
| `/api/v1/bookings/**` | `ADMIN` or `CLIENT` | 401 | 403 |

401/403 responses are returned in the same `ApiError` JSON shape as every other error
(`RestAuthenticationEntryPoint`/`RestAccessDeniedHandler`); a login with bad credentials also
returns 401 in that same shape. This is intentionally a minimal, assignment-scoped scheme — see
the project's interview-prep notes for what a production version would add (per-customer booking
ownership, individual admin accounts, refresh tokens, etc.).

### Example walkthrough (once the app is running on :8080)

```bash
# 1. Log in as admin, capture the token
ADMIN_TOKEN=$(curl -s -X POST localhost:8080/api/v1/auth/login -H 'Content-Type: application/json' \
  -d '{"username": "admin", "password": "admin123"}' | python3 -c "import json,sys; print(json.load(sys.stdin)['token'])")

# 2. Log in as client, capture the token
CLIENT_TOKEN=$(curl -s -X POST localhost:8080/api/v1/auth/login -H 'Content-Type: application/json' \
  -d '{"username": "client", "password": "client123"}' | python3 -c "import json,sys; print(json.load(sys.stdin)['token'])")

# 3. Create a schedule (admin) — generates bookable instances for the next year
curl -H "Authorization: Bearer $ADMIN_TOKEN" -X POST localhost:8080/api/v1/admin/schedules -H 'Content-Type: application/json' -d '{
  "flightNumber": "XY101", "sourceAirportCode": "DXB", "destinationAirportCode": "LHR",
  "departureTime": "09:30:00", "arrivalTime": "13:45:00", "aircraftId": 1,
  "daysOfOperation": ["MONDAY", "WEDNESDAY", "FRIDAY"]
}'

# 4. Search flights on a matching date — public, no auth
curl "localhost:8080/api/v1/flights/search?source=DXB&destination=LHR&date=2026-07-06"

# 5. View the seat map for a returned flightInstanceId — public, no auth
curl localhost:8080/api/v1/flights/1/seat-map

# 6. Book seats (client)
curl -H "Authorization: Bearer $CLIENT_TOKEN" -X POST localhost:8080/api/v1/bookings -H 'Content-Type: application/json' -d '{
  "flightInstanceId": 1, "passengers": [{"name": "Alice", "seatLabel": "1A"}]
}'

# 7. Cancel (client)
curl -H "Authorization: Bearer $CLIENT_TOKEN" -X POST localhost:8080/api/v1/bookings/<reference>/cancel
```

### Onboarding airports & aircraft (admin)

Airports and aircraft ship pre-seeded via Flyway (`V7`/`V8`) but can also be onboarded live:

```bash
curl -H "Authorization: Bearer $ADMIN_TOKEN" -X POST localhost:8080/api/v1/admin/airports -H 'Content-Type: application/json' -d '{
  "code": "AUH", "name": "Zayed International Airport", "city": "Abu Dhabi", "country": "United Arab Emirates"
}'

curl -H "Authorization: Bearer $ADMIN_TOKEN" -X POST localhost:8080/api/v1/admin/aircraft -H 'Content-Type: application/json' -d '{
  "type": "A321", "seatRows": 34, "seatLetters": "ABCDEF"
}'
```

Both are create-and-read only (`GET .../{code}` / `GET .../{id}`) — no update/delete, same
immutable-after-creation pattern as flight schedules, since changing a seat grid or airport after
schedules/bookings reference it would invalidate data already derived from it.

## Design decisions

### Schema

- `airport`, `aircraft` — pre-seeded reference data (Flyway `V7`/`V8`), also onboardable live via
  `POST /api/v1/admin/airports` / `/api/v1/admin/aircraft` (ADMIN only) — create-and-read only, no
  update/delete. Aircraft seat labels (`"1A"`.."30F"`) are never stored — they're derived from
  `seat_rows`/`seat_letters` on demand (`SeatMapCalculator`).
- `flight_schedule` — the reusable template (flight number, route, times, aircraft,
  days-of-operation). Immutable after creation — no update endpoint, per the assignment's
  assumptions.
- `flight_instance` — one row per concrete bookable date. See **Flight instance generation**
  below for why these are materialized rather than computed on the fly.
- `booking` / `booking_seat` — a booking's seat holds. See **Booking algorithm** for why
  cancellation *releases* (`released_at`) rather than deletes these rows.

### Flight instance generation strategy

**Decision: materialize eagerly**, not dynamic/on-the-fly generation, not a lazy hybrid.

When a schedule is created, the system immediately generates one `flight_instance` row for every
date in `[today, today + 364]` whose day-of-week matches the schedule's days-of-operation
(`FlightInstanceGenerationService`). A 3-day/week schedule yields ~156 rows, not a flat 365 — only
matching days are materialized.

**Why**: seat bookings need a stable foreign key to attach to for a specific date — a booking is
"seat 1A on XY101 on 2026-07-06", not "seat 1A on XY101 in general". Materializing eagerly means
search, seat-map, and booking all query a single indexed table with no runtime date-matching
logic, at the cost of a bulk insert (at most 365 rows) when a schedule is created — trivial for
MySQL. Computing candidate dates at search time was considered but rejected: it would still
need *some* concrete identifier for seat/booking rows to reference, so it doesn't avoid having a
flight-instance concept — it just defers creating it to first-booking-attempt, adding complexity
(handle "does this instance exist yet" on every booking) for no real benefit at this scale.

**Known limitation**: the window is fixed at the schedule's *creation* time, not rolling. A
schedule created today has no instances beyond day 364 even if queried a year later. Rolling the
window forward would need a scheduled job (e.g. nightly) that generates each active schedule's next
day of instances — a natural next step, intentionally not implemented here (out of scope).

### Concurrency strategy

**Decision: a unique index (emulating a partial index), not row-level locking.**

`booking_seat` needs a unique constraint on `(flight_instance_id, seat_label)` that only applies
while a hold is active (`released_at IS NULL`) — Postgres offers this natively as a partial
index, but MySQL has no partial/filtered index support. It's emulated instead with a generated
column that collapses to `NULL` (and is therefore exempt from the unique check, since MySQL — like
Postgres — allows unlimited `NULL`s in a unique index) whenever a hold is released:
```sql
active_seat_label VARCHAR(5) GENERATED ALWAYS AS (IF(released_at IS NULL, seat_label, NULL)) VIRTUAL
...
CREATE UNIQUE INDEX uq_booking_seat_active
    ON booking_seat (flight_instance_id, active_seat_label);
```
Only one *active* (non-released) hold on a given seat is allowed at a time. `BookingService
.createBooking` inserts all of a booking's seat rows in one `@Transactional` method and calls
`saveAllAndFlush(...)` immediately afterward — this is essential: without the explicit flush,
Hibernate would defer the inserts to commit time, and a constraint violation would surface *after*
the method had already returned, too late for the `catch` to ever run. If a concurrent transaction
already holds one of the requested seats, MySQL (InnoDB) blocks the second inserter on that key until the
first transaction resolves, then raises a constraint violation independent of isolation level — no
`SERIALIZABLE` or `SELECT ... FOR UPDATE` needed. Because every seat in one request shares a single
transaction, a conflict on *any* seat rolls back the *entire* booking — there is no partial-success
case; a two-seat request either gets both seats or none.

**Rejected alternative**: `SELECT ... FOR UPDATE` on the `flight_instance` row before checking
availability. Also correct, but serializes *every* booking attempt on a flight, even two requests
for two completely different seats — worse scalability than contending only on the literal seat
being fought over, which is what the unique-index approach achieves.

A best-effort pre-check (`BookingService.validateSeatRequests` queries for already-held seats
before attempting the insert) exists purely for a nicer error message sooner — it is **not** the
safety mechanism; the race is actually closed by the DB constraint regardless of whether the
pre-check runs.

Separately, `booking.version` (JPA `@Version`, optimistic locking) guards against a concurrent
double-cancel race on the same booking's status field.

### Why seats are soft-released, not deleted, on cancellation

`booking_seat.released_at` is set (not the row deleted) when a booking is cancelled. This keeps a
cancelled booking's original seat assignments inspectable via `GET /bookings/{reference}` — useful
for audit/support — while the unique index (`uq_booking_seat_active`, active only while
`released_at IS NULL`) means a released seat is immediately available for a new booking again.

## Search algorithm

`FlightSearchService.search(source, destination, date)`:
1. Query `flight_instance` by `(source_airport_code, destination_airport_code, flight_date)` — a
   single indexed lookup. "Only flights operating on the requested date" falls out for free: a row
   only exists for a date if generation already matched it against the schedule's
   days-of-operation, so there's no runtime day-of-week check at search time.
2. For each matching instance, available seats = aircraft's total seat count (`SeatMapCalculator
   .totalSeats`, derived from `seat_rows × seat_letters.length()`) minus the count of currently
   active `booking_seat` rows for that instance.
3. Returns `flightInstanceId` (needed to then call seat-map/booking — a hole in the literal field
   list the spec doesn't otherwise address), flight number, departure/arrival timestamps, and the
   available-seat *count* (not a seat list — that's the seat-map endpoint's job).

## Booking algorithm

`BookingService.createBooking(flightInstanceId, passengers)`:
1. Load the flight instance (404 if unknown).
2. Validate: no duplicate seat labels within the request; every requested seat label exists on the
   aircraft's configuration (`SeatMapCalculator.isValidSeatLabel`).
3. Best-effort pre-check for already-held seats (nicer error message, not the safety mechanism —
   see **Concurrency strategy**).
4. Persist the `booking` row (`CONFIRMED`), then persist all `booking_seat` rows and flush
   immediately, inside one transaction.
5. On a unique-constraint violation (`DataIntegrityViolationException`), the whole transaction
   rolls back and a `SeatUnavailableException` → HTTP 409 is returned.
6. On success, returns the booking reference (UUID/PNR), flight number, flight date, passenger
   count, assigned seats, and status.

## Cancellation algorithm

`BookingService.cancelBooking(reference)`:
1. Look up the booking by reference (404 if unknown).
2. If already `CANCELLED`, return the current state unchanged (idempotent — not an error).
3. Otherwise, set status to `CANCELLED` and save with the booking's `@Version` guard; a
   concurrent conflicting update raises `ObjectOptimisticLockingFailureException` →
   `BookingStateConflictException` → HTTP 409.
4. Release all of the booking's active seats by setting `released_at` (not deleting them — see
   above), making them immediately available for new bookings.
5. Returns the updated booking, still showing its original seat assignments.

## Assumptions

- Single airline. `/admin/...` endpoints require an `ADMIN` JWT (see **Authentication**);
  `/bookings/...` accepts either seeded role's JWT. This is a minimal, assignment-scoped auth
  scheme — no per-customer booking ownership, no individual admin accounts, no refresh tokens.
- One seat belongs to one booking at a time; one booking is for a single flight instance.
- Aircraft seat maps are fixed; flight schedules are immutable after creation.
- Airports and aircraft are preloaded (Flyway seed data) and also onboardable live via admin API;
  both are create-and-read only — no update/delete, since schedules/bookings may already reference
  them.
- Booking window is 365 days from a schedule's creation date, fixed at creation (not rolling —
  see **Flight instance generation**).
- All timestamps are stored/returned as UTC; no timezone conversion.
- Passenger info is name-only. "No passenger validation required" is interpreted as no
  semantic/format checks (no length/charset/identity rules) — but the field must still be
  non-blank, since an empty name is a malformed request, not a judgment about valid names.
- An arrival time-of-day that is not strictly *after* the departure time-of-day
  (`arrival_time <= departure_time`) is treated as landing the next calendar day.

## Testing

`./mvnw test` runs against a real MySQL via Testcontainers:
- `FlightScheduleGenerationIT` — schedule creation generates the expected instance count; search
  only returns results for operating days.
- `BookingFlowIT` — booking updates the seat map, cancellation releases the seat for rebooking,
  and a cancelled booking's original seats remain inspectable; duplicate/unknown seat requests are
  rejected.
- `BookingConcurrencyIT` — `N` threads race via real HTTP requests (not `MockMvc` with a
  transactional test, which would hide the real race in a single DB connection) for the same seat;
  exactly one succeeds.
- `SeatMapCalculatorTest`, `DaysOfWeekConverterTest` — plain unit tests, no Spring context.

A fixed `Clock` bean (`FixedClockTestConfig`, `@Primary` in tests) replaces `Clock.systemUTC()` so
"today"-dependent generation counts are deterministic regardless of when the suite runs.

Since `SecurityConfig` protects `/admin/**` and `/bookings/**`, every IT logs in against
`POST /api/v1/auth/login` with the same two seeded users described in **Authentication**
(`AuthTestSupport.login(...)`) and sends the returned JWT as a Bearer token on subsequent calls —
there's no test-only security bypass, so the suite exercises the real auth path, not a mocked one.
